Honest Limitations

  • Two-tier design, on purpose. The rigorous version of this analysis is the Stage 1-7 notebook pipeline in this repository (COGS, shipping, and payment-fee costs modeled separately, computed in Python) -- that notebook is the source of truth for exact figures. This page trades some of that precision for something the notebook can't do: run entirely in a browser, load your own CSV, and redraw every chart live. It works from a single generic "cost" column per transaction instead of the notebook's three-way cost breakdown, so its numbers are directionally consistent with, not always numerically identical to, the notebook's.
  • Returns reverse both revenue and cost on that line. The notebook pipeline is more precise here: it keeps the non-refundable shipping/payment-fee cost on a return, since that money was already spent regardless of what the customer does next. Reversing both fully is a reasonable approximation for a live, single-cost-column tool -- it only diverges from the notebook's number where returns and per-line fulfillment cost both matter.
  • Marketing cost is allocated per transaction row, not per order. This engine has no order-ID concept, so it divides each channel's spend evenly across the rows attributed to it (spend ÷ rows-per-channel) rather than the notebook's per-order-line share. For orders with more than one line item, this slightly over-charges each line -- a known, bounded approximation that stays directionally correct. The exact per-order allocation lives in the notebook's fashion.py module.
  • Cohort window, dead-stock bar, and CAC assumptions are fixed defaults. This page uses a 6-month cohort window, a 3-months-available / ≤15%-sell-through dead-stock cutoff, and a 3.5-order assumed customer lifetime for LTV:CAC -- the same defaults as the notebook's fashion_config.py, chosen as common industry conventions rather than tuned to any one dataset. They're baked into this page's code, not exposed as UI controls.
  • Month annotations are user-supplied context, not a seasonality model. Labeling a month "Diwali" or "stocking problem" doesn't separate that event's effect from ordinary month-to-month seasonality the way a real forecasting model would -- one-off events (campaigns, PR, stockouts) are annotated by the operator, not statistically distinguished by this tool. It's a label for a human to interpret, not an estimated effect size.
  • The forecast only claims seasonality it can actually back up. A calendar month is only treated as seasonal if it repeats across at least 2 distinct years in your data -- with under a year of history (like the bundled DIY-kits default, 6 months), every month is forecast on trend alone, flagged "insufficient history to confirm seasonality," rather than extrapolating from a single observed spike. Seasonal factors are computed AFTER removing a fitted trend line, not as a raw ratio to the series average, specifically so a genuine growth or decline trend can't leak into and distort the seasonal numbers. The backtest error (WAPE) is computed on your own most recent 3 months, not assumed from the notebook's -- it will differ dataset to dataset, and a single straight trend line fit across all of history will underfit a business whose growth rate is itself changing (accelerating, plateauing, a step change), the same limitation any linear-trend model has.
  • Seasonality Source is an explicit choice, not a silent default. The Demand Forecast panel's "Let the tool project" option (the default) reuses the forecast engine's own output verbatim, including the 2-confirmed-prior-years rule above -- with under 2 years of history it is always labeled "Trend projection," never "seasonal forecast," and never invents a seasonal spike for a month that hasn't earned one. "I'll set it" replaces that with the CEO's own typed % change per month (default 0, i.e. flat trend), applied to that month's trend run-rate and explicitly labeled "your input, not a model prediction." Whichever is active also becomes the Goal Planner's next-quarter baseline -- both panels read the same computeSeasonalityBaseline() output, so they can't silently disagree about what "next quarter" means.
  • External Cost Sensitivity is a calculator, not a forecast. It never looks up or predicts a USD, crude, or any other external price -- every factor's exposure % and price move % are numbers the CEO types in (or, with an optional Cost Breakdown file, a suggested starting point per factor that's still fully editable), and a new panel starts with a single 0%-exposure factor. It also never infers that any historical cost change WAS caused by an external factor; it only computes what hypothetical moves would do to margin from today's numbers. Each factor is assumed to hit its own distinct, non-overlapping slice of cost -- the panel warns, but does not block, if the exposure percentages entered across factors add up to more than 100%. With a Cost Breakdown file, each cost component is matched by name against a small built-in Commodity Linkage Library (polyester/synthetic fabric, cotton, plastics/packaging, imported dyes/chemicals, domestic labour, freight) to suggest a driver and a pass-through multiplier -- these are curated, generic reference defaults for a D2C goods business, never a measured elasticity and never derived by regressing this business's own cost history against any macro series. Only the exposure % (each component's actual share of total cost) is real data; every pass-through is a starting assumption, labelled as such, and fully editable. A component whose name doesn't match the library is shown as "Not linked to library" rather than assigned a guessed driver. If a Macro Prices file is also supplied, the panel can suggest a price move % from the latest value vs. a baseline month the CEO picks -- still just a typed-in scenario, never an auto-applied prediction.
  • Goal Planner is a single goal-seek calculator with two levers, each grounded in a different measured ratio -- never a cross-category substitution guess. A PRODUCT-MIX lever used to live here (shift units between categories) and has been removed entirely: it rested on an uncalculable assumption (shifted units selling through at the destination category's own margin, with no way to verify a customer would actually have bought the pricier item instead of walking away) that neither remaining lever shares. The PRICE lever (raise average selling price up to a cap, units held fixed) rests on the unmodeled assumption that demand holds at the higher price -- real price elasticity isn't estimated anywhere in this tool -- but its baseline (current revenue) is real. The AD-SPEND lever computes a whole-business, BLENDED ROAS -- total company revenue ÷ total ad spend, both from the last 3 months of the Marketing Spend file's own calendar (both sides normalized to the same "YYYY-MM" month-key shape before comparing, so a file spelling dates as "2026-05-01" still matches Transactions' "2026-05" and revenue is never wrongly read as zero) -- then applies EDITABLE, geometrically diminishing returns to extra spend (default decline 0.5%/point, deliberately gentle -- informed by, but not fit to, a real observation of a large spend jump seeing marginal ROAS fall from ~2.5x toward ~1.85x). Requires a Marketing Spend file; without one this lever contributes nothing and says so, while the price lever still works standalone. Being blended is a real limitation, stated plainly: the ROAS doesn't separate out revenue that would have happened anyway (organic, repeat, offline), so it can overstate what the ad spend itself is driving. In PROFIT mode the ad lever nets its own extra spend out of its contribution (revenue × measured margin − spend) and its useful range is capped wherever marginal PROFIT (not just marginal revenue) stops paying for itself -- since margin is under 100%, that point comes before revenue's own 1x ceiling, so a path never recommends spending further just because revenue would still technically grow. The next-quarter baseline reuses the Demand Forecast panel's seasonal forecast when there's enough history for one; with less, it falls back to a flat run-rate, labeled as such rather than passed off as a seasonal forecast it isn't. Ranked paths (Price-led / Ad-led / Balanced) each show both levers' moves and an achieved result recomputed independently from those exact moves, never assumed equal to the target; if no combination within both caps reaches the target, the panel says so plainly -- the closest reachable % and which cap is binding -- rather than stretching either assumption to force a "yes".
